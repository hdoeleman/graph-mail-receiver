# 1. How mail is retrieved from Microsoft Graph

Status: accepted

## Context

The app reads the Inbox of one mailbox through Microsoft Graph, and has to work without credentials for trying it out. It compares two ways to call Graph from Java: Spring's own HTTP client support and Microsoft's Graph SDK. Besides showing the newest mail, it must be able to fetch only mail it hasn't fetched before and keep that mail, without losing any when a fetch is interrupted. A temporary web page shows the result.

## Decision

- **Three modes, chosen per pull.** `demo` (generated emails, no credentials), `rest` (Graph REST API through Spring) and `sdk` (Microsoft Graph Java SDK). Each pull names its mode (`GET /api/emails?mode=...`), so the server keeps no "current mode" and viewers don't affect each other. `graph.mode` (default `demo`) sets the default mode: the one the page preselects, and the one a pull without `mode` uses. `MailSourceConfig` creates every source into one `MailSources` registry.
- **Pull, not push.** A regular pull reads the newest Inbox messages (`GET /users/{mailbox}/mailFolders/inbox/messages`); a "new mails only" pull reads the Inbox delta (below). Graph change notifications (webhooks) are not used: they need a publicly reachable HTTPS endpoint and subscription renewal, which pull-on-demand does not need.
- **App-only authentication (OAuth2 client credentials) with the `Mail.Read` application permission**, in both Graph modes. No user password is stored and no user sign-in is needed. The cost is that the permission covers every mailbox in the tenant until an Application Access Policy (or RBAC for Applications) restricts it to the intended mailbox; the README documents this.
- **REST mode: a Spring HTTP service client (`@HttpExchange`) with Spring Security's OAuth2 client.** `GraphMailApi` is an interface registered with `@ImportHttpServices`; Spring generates the implementation on Boot's `RestClient`. `@ClientRegistrationId` on it makes Spring Security fetch, cache and refresh the token (refreshed 60 s before expiry), so the app has no token code of its own. This is Spring's current approach for declarative clients; Spring Cloud OpenFeign is feature-complete and points new code here.
- **SDK mode: `GraphServiceClient` with azure-identity's `ClientSecretCredential`**, which caches tokens itself. The SDK's typed request builders and models replace hand-written DTOs, and its middleware retries throttled requests (429/503/504).
- **Rejected tokens are dropped.** App roles are fixed in a token when it is issued, so a token from before admin consent keeps failing until it is replaced. After a 401 or 403 from Graph, REST mode removes the token from Spring Security's cache, and SDK mode rebuilds its Graph client with a new credential (whose token cache is empty), reusing the same HTTP clients. REST mode needs its own failure handler for this: Spring Security's interceptor drops nothing by default, and its ready-made handler covers `invalid_token` (401) and `invalid_grant` but not `insufficient_scope` (403). A 401 is retried once; a 403 fails the pull, and the next pull uses a new token.
- **Bounded HTTP calls in both modes.** `spring.http.clients.connect-timeout` (5 s) and `read-timeout` (30 s) apply to every request. In REST mode, Boot's HTTP service client auto-configuration sets up the Graph group's client with them, and the token request uses a `RestClient` built from Boot's `RestClient.Builder`; Spring Security's default token client is built with `RestClient.builder()` and would ignore these settings. In SDK mode, `SdkMailSource` passes them to the SDK's OkHttp client and to the credential's azure-core HTTP client. `spring.http.clients.imperative.factory` is pinned to `jdk`, because azure-identity brings Reactor Netty along and Boot would otherwise use it for `RestClient`.
- **Plain-text bodies.** Both Graph modes send `Prefer: outlook.body-content-type="text"`, so Graph returns bodies as text, not HTML.
- **"New mails only" through a Graph delta query, stored in a database.** Graph tracks the sync position: `.../inbox/messages/delta?changeType=created` returns pages of new messages ending in a deltaLink, and following that link later returns only messages created since. The app stores the mails and skips ids it already has. Both Graph modes implement the delta (`DeltaSource`); `NewMailService` runs the sync and stores the results.
  - **Storage: an H2 file database with Spring Data JDBC and Flyway.** Mails (`email`, keyed by the Graph message id) and one sync state per mailbox (`sync_state`) are stored. Spring Data JDBC over JPA: two tables of immutable records, no lazy loading or sessions. Flyway over Liquibase: plain SQL migrations, and Apache 2.0 rather than Liquibase 5's FSL, with none of Liquibase's extras (rollback, preconditions, database-independent changelogs) needed here.
  - **Stored once, by immutable id.** A mail counts as new when its id is not stored yet, whichever mode fetched it. Delta requests send `Prefer: IdType="ImmutableId"`, because default Outlook ids change when a mail moves between folders.
  - **Progress is saved with every page.** Each page's new mails are written in one transaction together with the sync's progress: the next page's link while the sync is unfinished, the deltaLink once it completes. A pull that stops part-way (a failure, or the cap of 200 pages, about 10,000 mails) leaves the next page's link, and the next pull continues there.
  - **Each sync remembers where it started.** Until it completes, the sync state keeps its start point: the newest stored mail when it began, or `graph.initial-sync-window` (30 days) ago when nothing was stored. Outlook evicts delta tokens from a limited cache, so links expire as a normal event: `410 Gone`, or a 4xx with an error code such as `syncStateNotFound`. The sync then starts again from that start point (`$filter=receivedDateTime ge <start>`, de-duplicated by id). Pages an interrupted sync hadn't reached are therefore not skipped, and older mail is not fetched again. The restart link Graph may offer in `Location` is not used: it repeats the very first query, which is unbounded and older than any start point. A reset forgets the links but keeps an unfinished sync's start point.
  - **Graph's 5,000-message cap.** With a `$filter`, Graph returns at most 5,000 messages per delta sync, in no fixed order unless asked; the start request asks for `$orderby=receivedDateTime desc`, the only ordering delta supports, so a capped sync keeps the newest mail, and reaching the cap is logged as a warning.
  - **One sync state per mailbox, shared by both Graph modes**, since Graph's links are plain URLs either can follow. Pulls are serialized. Demo mode simulates new mail and stores nothing.
- **Graph settings are checked at startup.** Without the tenant id, client id, client secret or mailbox, the rest and sdk modes are unavailable, and `/api/modes` names the missing settings. Starting with `graph.mode` set to `rest` or `sdk` while any is missing fails at startup instead. Ids and the mailbox are stripped of surrounding whitespace.
- **The web page and its `/api` endpoints are temporary.** `index.html`, `MailController` and its endpoints (`/api/emails`, `/api/modes`, `/api/emails/new`, `/api/emails/stored`, `/api/sync/reset`) exist only to try the Graph integration by hand and will be removed. The page offers a mode switch, greys out unavailable modes with the reason, remembers the last choice in the browser, and renders bodies with `textContent`. Spring Security is on the classpath for its OAuth2 client only; `SecurityConfig` leaves every request open.
- **Spring Boot 4 on Java 25**, the current generations, which also bring Spring Framework 7's HTTP service registry and Spring Security 7's `@ClientRegistrationId` support used above.

## Consequences

- A regular pull returns the newest N messages (max 50) without paging or de-duplication; "new mails only" is the de-duplicated, stored path.
- The database file holds mailbox content unencrypted (H2 supports `CIPHER=AES` if that changes). Mail deleted or moved in the mailbox stays stored; the sync only adds.
- A first sync, or one after a long gap, over more than 5,000 mails in its range stores only the newest 5,000 of them; a shorter `graph.initial-sync-window` avoids that for busy mailboxes.
- Flyway 12.4 (managed by Spring Boot 4.1.1) logs at startup that H2 2.4 is newer than the H2 versions it was verified with (2.3).
- Three HTTP stacks are on the classpath: the JDK client (REST mode), OkHttp (the SDK's Graph requests) and Reactor Netty (azure-identity's token requests).
- In REST mode, a throttled request (429) fails the pull with the error; only the SDK retries by itself.
- Concurrent pulls that find no valid token each request their own token; each such request is bounded by the timeouts.
- Because the page and endpoints are temporary, they have no authentication and listen on all network interfaces. They are not meant to run with real credentials on a shared network.
